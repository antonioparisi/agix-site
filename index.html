01 / how a run flows

Describe it. Approve the plan. Merge the work.

  1. PLAN

    A PM reads the code and plans

    Goal, tasks in order, the files each touches, what counts as done and the edge cases. Agix checks the plan and lists what to look at, with one-click fixes.

    you: approve, or request changes

  2. BUILD

    The crew works in worktrees

    Builders and testers each get a git worktree. Finished work is handed to whoever builds on it. Questions for you show up with an answer box.

    you: answer, steer, stop a turn

  3. MERGE

    You merge, in the right order

    Each worktree's diff with the tasks it covers and what testers said. Try them all together first; a merge that would conflict is refused and changes nothing.

    you: merge all, or one by one

  4. PR

    Or open a PR the crew keeps fixing

    Agix pushes a branch and opens the PR. Failing checks and review comments are picked up and addressed by a PR fixer, round by round.

    you: review it on GitHub

02 / mission control

Everything the crew does, where you can see it

Every clip below is the real Mission control, recorded against a local daemon with demo data: a storefront team adding CSV export to its orders page.

Start

Three ways to start: chat, plan, or build a feature

Say what you want, pick the project, the runtime and its model. A chat is one agent you talk to. A plan scopes something new without starting a crew. Build a feature hands it to a PM, which reads the code (it cannot change it) and submits a plan.

  • Projects found on your machine, searched from the keyboard
  • Read only, Edit files, or Edit + run commands
  • Pick a saved crew, or let the PM choose one

Plan review

A plan you can check before anything changes

Tasks in order with their files and estimates, acceptance criteria with the test that proves each, edge cases with their decisions. Agix lists what to look at: two tasks writing the same file at once, a criterion nothing tests. One click fixes it and makes a new version.

  • Task graph with the critical path, and a timeline per agent
  • Rest on a task to see what it covers and touches
  • Approve and start crew, or send your notes back

Build

The crew live, in words

Each agent says what it is doing right now: editing a file, running the tests, waiting on a teammate. Messages between agents show in one feed, hand-overs included. When one asks you something, the answer box is right under the question, and your answer goes back to whoever asked.

  • Task progress for the run and for each agent
  • Write to the PM, or to anyone with @name
  • Cost and context use on every agent's card

Views

List, lanes, board, graph

Lanes lay the run out over time, a lane per agent and every message an arrow, with why anything is waiting. The board moves tasks across as the crew reports them, blocked ones with the reason. The graph shows who talks to whom, and takes new personas by drag and drop.

  • Arrow keys walk through messages
  • Ask the PM for another task from the board
  • The view you left is the view you come back to

Up close

One agent, up close

Its tasks as a checklist, what it spent, how full its context is, and the worktree it works in: branch, folder, and a button to open it in your editor. The live view is one timeline: what it said, the steps it took, the messages that reached it. Write to it from there; it reads it after its current step.

  • Stop a turn, resume it, or move the agent to another runtime
  • Context bar turns amber at 70%, red at 85%; compact in one click

Changes

Comment on a line; the agent that wrote it answers

The Changes view lists every file the crew is changing, live, with who changes it and its diff. A file two agents both change is flagged, since that is where their merges would clash. Comments on lines are drafts until you send them; the agent gets each with its file, line and code, and its answer shows under the line.

  • Drafts survive a reload
  • The same comments at the merge stage

Merge

Merge in the right order, after trying it all together

Each worktree's changes in the order to merge them, work others build on first, and why. The tasks each covers and the last word from testers and reviewers sit above the diffs. Try them all together merges into a scratch copy and says whether they combine. Merge all, in order stops at the first refused merge and says what it did.

  • Worktrees holding the same work are said once
  • Your checkout is untouched until you merge

Pull requests

A PR the crew keeps fixing

Instead of merging here, open a PR: the worktrees go on a new branch, pushed, with a PR into main. When a check fails or a reviewer comments on a line, a PR fixer addresses it in a round: fixes the code, pushes, replies to the comment. Up to three rounds before it asks you; pause it any time.

  • A PRs page across all your runs
  • Uses the gh you are signed in to

When things go wrong

Out of tokens, going in circles, gone quiet

An agent that hits its usage limit is paused with its work saved, and can carry on on another runtime, keeping its conversation. Two agents messaging each other back and forth without settling it are paused and shown, so you or the PM decide. A crashed agent restarts with its session; a quiet one can be nudged.

  • Fallback runtimes per persona, used on their own
  • Stop one agent's turn; its messages wait until you resume it

Needs you · ⌘J

One inbox for everything waiting on you

Plans to approve, questions, merges waiting, agents in trouble, budgets and context running out, across every run. Work through it from the keyboard: J K to move, R to answer in place, A to approve a plan, Enter to open it where it is dealt with.

  • Browser notifications for what starts waiting while you are elsewhere
  • Each item with its one-click fix

And the rest of the day

While you were away · ⌘K

Back after a night, Home says what changed in each run, what waits on you first. ⌘K searches runs, agents and messages.

Budgets, cost and limits

Spend and tokens per run and per agent, a budget that turns amber near it, and the $ panel: how much of each subscription's 5-hour and weekly windows is used.

Personas and crews

Roles agents play, with who plays them: runtime, model, fallbacks, a second opinion. Write with AI drafts the instructions. Save crews, or import a repo's .claude/agents.

On your phone

Approve plans, answer questions and move a stuck agent from your phone. The daemon listens on this machine only; turn on phone access and it also listens on your Tailscale address, never the open network.

03 / new in the bridge

Agents that can check their own work

The bridge is what every agent gets from Agix: messages, tasks, hand-overs. It now does more of the work a developer does to call something finished.

A browser of its own

Each agent gets its own browser to look at what it built. Local pages only: it cannot browse the web with it.

Dev servers on their own ports

Two builders can each run the app from their worktree at the same time, without fighting over port 3000.

Test logins, handled by Agix

When a page needs signing in, Agix does it with the project's test account. Agents never see the password.

Done means proven

A task counts as done only once Agix has run its happy and unhappy checks, with screenshots, not when an agent says so.

04 / safety

Built to be left running

Local only
The daemon listens on 127.0.0.1, and every call needs its token. Phone access adds your Tailscale address and nothing else.
Worktrees, not your checkout
Builders and testers each work in a git worktree of their own. Your checkout stays as it is until you merge.
Never merges for you
Merging is your click. A merge that would conflict is refused and changes nothing. A PR goes to GitHub for review.
Your sign-ins stay yours
Each runtime uses its own sign-in. Agix never asks for or stores credentials, and agents never see test passwords.
Limits you set
What agents may do (read, edit, run commands), a budget per run, and a loop guard that pauses agents going in circles.
Only the bridge
Agents get the Agix bridge, not your other MCP servers. The PM and reviewers only read.

05 / open source, soon

Open source, soon.

Agix is being finished before its code goes public, under the Apache-2.0 license. It runs on your machine with Node 24 or later and the runtimes you already use, signed in your usual way, and keeps its database, logs and worktrees in ~/.agix. Starting it will look like this:

zsh
# from the repository
$ npm install
$ npm run build:web
$ npm run daemon -- --open
Mission control on http://127.0.0.1:<port>/#token=…

# later, from anywhere
$ agix ui
